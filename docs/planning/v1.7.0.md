## 二、本版定位与出口条件

**定位：不是「再加 10 个工具」，而是「先立三道护栏，再按批次扩量」。**

出口条件（每条都可被一条命令或一次点击验证）：

1. **R1 落地**：`registry.ts` 不再有手写条目，工具清单由 `meta.ts` 聚合。
2. **门禁合流**：CI 执行 `audit:meta --check` 与 `icons:check`，本地与 CI 判据一致。
3. **度量可用**：`pnpm report:bundle` 能报出全部工具 chunk 的数量与总体积（不再是 0）。
4. **批次 1、2 交付**：5 项全部通过第四节验收标准（批次 2 原定「视余量」，本版已一并交付）。
5. **预算未破**：首屏 gzip 不高于 v1.6.0 基线（文档记 166KB、`bundle-latest.json` 实测 169KB，A2 修复后以新数据为准），R1 落地后应净减；`index.html` 的 modulepreload 中不出现任何工具 chunk。

非目标（本版不做，避免范围蔓延）：工具级英文化（i18n 只覆盖外壳）、API 响应契约统一、AI 调用收敛（12 个 AI 工具页状态机各自为政）。

## 三、Track A：前置门禁（必须先于任何新工具）

### A1 — R1：元数据单一事实源

**方案**：`registry.ts` 改为构建期聚合，不再手写。

```ts
const modules = import.meta.glob<{ meta: ToolMeta }>('@/tools/*/meta.ts', { eager: true })
export const toolRegistry: ToolMeta[] = Object.values(modules)
  .map(m => m.meta)
  .sort(/* CATEGORY_ORDER 序 + id 字典序，保证稳定 */)
```

**为什么这是最短路径**（本版明确采纳，替代初版的「手工加第 145 条」）：

1. 不需要代码生成器、不新增 devDep——`meta.ts` 已是纯 const、无副作用，`import.meta.glob` 非 eager 的懒加载表已在 `src/lib/tool-loader.ts` 验证可用。
2. 一次性消灭「加工具改两处」的漂移源，也顺带废掉孤儿脚本 `sync-meta.mjs`。
3. 收益是**维护性**，不是体积：单做 R1 首屏反而 +4KB（模块化边界与展示顺序表的开销），详见第八节实测。

**连带改动与风险**：

- `scripts/audit-meta.mjs` 删除对 `registry.ts` 的文本解析，三方校验退化为「目录 vs meta」两方；
- 同时把 `name/category/icon` 漂移从 **warn 升级为 error**——历史上 19 处 meta/registry 名称不一致正是以 warn 形式一路漏到 v1.6.0 才被批量修复；
- 首页「全部工具」顺序由人工 Phase 顺序变为分类序，属可见变化（见第七节待决策 1）。

### A2 — 修 `report-bundle.mjs`

递归读取 `dist/tools`，工具 chunk 单列统计并计入总量。**这是所有体积约束的前提**：当前脚本对 `dist/assets` 做非递归 `readdirSync`，再用 `startsWith('tools/')` 过滤，条件恒假。

### A3 — CI 补门禁

`audit:meta --check`、`icons:check`、`check-store-selectors` 进入 CI。否则 A1 的收益在第一周就会被一次手滑抵消。

### A4 — 工具数硬编码收口

`index.html` 的 description 改为不含具体数字的表述；README 与 `docs/ARCHITECTURE.md` 中的 144 登记为「发布时统一更新」，本版不改（改文档不在本次交付边界内）。

### A5 — i18n 边界（决策记录）

现状是外壳双语、工具内部纯中文。本版新工具只保证 `meta.nameEn` 字段与中文 UI，**不承诺工具内英文**；英文入口维持现状。写明这一点，是为了避免按「完整双语」验收。

## 四、Track B：工具扩展

### 4.1 排序依据（替换初版的「使用频率」）

项目无使用数据，原依据无法支撑排序。改用三条可核验准则：

- **C1 缺口真实性**：现有工具或浏览器 DevTools 的替代路径有多大摩擦（可查代码验证）。
- **C2 交付风险**：新依赖体积 + 运行时复杂度（Worker / 长连接 / 大文件）。
- **C3 复用度**：能否复用 `packages/core` 或既有工具管线。

排序原则：**C1 定价值、C2 定挡位、C3 只在同挡位内做取舍**。一个高价值但会长期腐蚀工程质量的功能，比一个低价值但零风险的功能更该延后。

### 4.3 对初版的事实修正

| # | 初版表述 | 实际 | 修正 |
|---|---|---|---|
| 1 | SVG → PNG「不重复」 | `image-convert` 已能把 SVG 文件转 PNG（`img` → canvas），但对无固有尺寸的 SVG 会得到 0×0 或 300×150，且无倍率、无透明控制、不能粘贴代码 | 改为「部分重叠」：先增强 `image-convert`，仍不足再拆独立工具 |

| 3 | HAR 分析 1 人日，验收含「>10MB 不卡死」 | 主线程 `JSON.parse` 10MB 不满足该标准 | 成本 1 → 1.5，明确走 Worker |
| 4 | 正则可视化「`regexp-tree` 约 60KB gzip」 | 未实测，估值不可采信 | 引入前实测，超标即放弃 |
| 5 | GraphQL「`graphql` 约 150KB gzip」 | 整包口径，可裁到 `graphql/language` | 限定子路径并单独申报体积 |
| 6 | Cookie「默认不写入 `HISTORY_ENABLED`」 | 该集合本身是白名单，未列入即不记录 | 删除该条，改为「无需额外动作」 |

### 4.4 重复性核对（修正后）

| 候选 | 现有相近工具 | 结论 |
|---|---|---|
| SVG → PNG | `image-convert`（SVG 文件可入，缺倍率/透明/代码输入）、`favicon-gen`（固定尺寸）、`svg-optimizer`（压缩）、`svg-to-data-uri`（内联） | **部分重叠**，先增强后拆分 |
| Cookie 解析 | `http-headers`（Header 字典）、`headers-check`（安全头检查）、`curl-converter`（整体转换，不拆属性） | 不重复 |
| 人民币大写 | `exchange-rate`（汇率换算，CNY 只是币种之一）、`number-unit`（物理单位） | 不重复 |
| 图片对比 | `image-compress`（压缩前后体积预览）、`tool-compare`（同一文本多工具）、`text-diff`（文本） | 不重复 |
| HAR 分析 | `json-formatter` 只能把 .har 当普通 JSON 格式化，无请求/耗时/域名语义 | 不重复 |
| WebSocket | `api-playground`、`json-rpc-test` 均仅 HTTP | 不重复 |
| PDF 合并 / 拆分 | 无任何 PDF 处理能力，仅 `mime-types` 收录 pdf 类型 | 不重复 |
| 三路文本合并 | `text-diff`（两路）、`json-merge`（JSON 深合并）、`env-diff`（.env 两路） | 不重复 |
| GraphQL 格式化 | `json-formatter`、`sql-formatter`、`yaml-json`、`xml-formatter` 均无 GraphQL 语法 | 不重复 |
| 正则可视化 | `regex-tester`（匹配高亮）、`regex-gen`、`ai-regex`（生成） | 不重复 |

### 4.5 验收标准（去模糊化）

- **image-convert 增强**：1x/2x/4x 输出尺寸正确；透明背景保留；粘贴 SVG 代码可直接导出；对无 `width/height` 的 SVG 以 `viewBox` 尺寸为准。
- **Cookie 解析**：解析 10 组真实样例；非法属性保留原值并标红，不静默丢弃；可复制为 `Cookie:` 请求头。
- **人民币大写**：表驱动 30 组覆盖 0、0.01、10.5、1000000.99、负数；写明金额上限与「零角零分」规则。
- **图片对比**：不同尺寸时以较大画布为基准、左上对齐、其余透明；差异比例 = 差异像素 / 并集像素。
- **WebSocket**：明确「仅支持浏览器可直连的 ws/wss」，Origin 被拒时给出明确错误，不静默失败。

## 五、实施顺序

1. **A1 → A2 → A3**：先让清单单一化、度量可信、门禁合流。
2. **批次 1**（三项）：每项完成即跑 `pnpm check`；批次结束跑 `pnpm build` + `pnpm report:bundle` 核对预算。
3. **批次 2**：两项各带独立 Worker（`diffWorker` 做 OffscreenCanvas 解码与像素比对，`harWorker` 做 JSON 解析与聚合）。规划原写「先抽一个共享 Worker 封装」，实际未抽：两者的入参、失败模式与产出完全不同，共享层只剩「requestId + 卸载时 terminate」这点骨架，抽出来反而多一层间接。共用的是模式，不是代码。
4. **批次 3**：留待 v1.8，触发条件为「有明确使用需求」或「依赖实测不超预算」。

新增工具流程（R1 之后，由五步降为四步）：

1. 建 `src/tools/<id>/`，写 `meta.ts`（`id` 必等于目录名）与 `index.tsx`（默认导出、`ToolLayout` 包裹）；
2. 从 `@core/xxx` 子路径导入，禁止 barrel；
3. `pnpm icons:gen && pnpm check`；
4. 确认 `registry` 自动收录（无需手改），并跑一次工具页烟测。

### 实施中发现的两处需要更正本文档的地方

1. **「R1 让首屏净减」不成立。** 实测：只做 R1 时首屏 169 → 173KB（+4KB）。原因是原先 `registry.ts` 的字面量在入口 chunk 里只有一份，改成 146 个 meta 模块后多了模块边界与展示顺序表的开销，体积并未减少。**R1 的收益是消除漂移，不是省字节。**
2. **存在第三份工具元数据副本，本文档此前未识别。** `src/i18n/locales/{zh-CN,en-US}.json` 里各有 122 个 `tools.<id>.name/description`，而工具名实际直接取自 `meta`，这些键没有任何代码引用，属于死数据。删除后每个语言包 709 → 222 行，首屏随之回落到 168KB。

### 度量基线（2026-11-06 实测）

- 工具数 **148**（网络 HTTP 18、图片媒体 9、单位换算 12），`pnpm audit:meta --check` 通过。

- 单测 **436 条通过**（新增 cookie 20 / rmb 37 / svg 10 / pixel-diff 6 / har 17）；E2E **197 条通过**（含 148 个工具页渲染冒烟）；`pnpm check` 全绿。
